# 当前 RTL 的输入范围边界

验证日期：2026-10-01。

本分析检查原设计在 `[-64,64]` 以外的实际行为，不修改生产 RTL，也不扩大 `plan.md` 中的原始接口承诺。
判定标准继续采用相对于数学真值 `exp(x)` 的相对误差 `<= 1e-5`，不是要求结果与正确舍入的 FP32 逐位相同。
FP32 溢出后另行比较输出类别，不能把 NaN 当作正确的 +Inf。

## 连续达标区间

结合原有 `[-64,64]` 全区间模型分析和本次扩展区间 RTL 穷举，包含零的连续 FP32 达标区间为：

```text
[-87.3365478515625, 88.72283172607421875]
```

这里的端点是精确可表示的 FP32 输入。往外移动一个 FP32 步长 `2^-17 = 0.00000762939453125` 就失败：

| 位置 | 精确输入 x | 输入位编码 | 当前 RTL 输出 | 正确舍入 FP32 exp(x) | 相对误差 / 状态 |
|---|---:|---|---|---|---|
| 负端最后达标 | -87.3365478515625 | `c2aeac50` | `007fffae` | `007fffe6` | `6.674177856931406e-6` |
| 负端紧邻失败 | -87.33655548095703125 | `c2aeac51` | `007fff2e` | `007fffa6` | `1.430375793825569e-5` |
| 正端最后达标 | 88.72283172607421875 | `42b17217` | `7f7fff67` | `7f7fff84` | `1.733951949473005e-6` |
| 正端紧邻失败 | 88.72283935546875 | `42b17218` | `7f800002` (NaN) | `7f800000` (+Inf) | 输出类别错误 |

负端最后一个达标输出已经是次正规数；它仅因误差仍低于阈值而达标，不能据此认为当前设计支持次正规数。
再前一个输入 `-87.33654022216796875` (`c2aeac4f`) 输出 `00800026`，仍为正规数。

扫描结果：正侧从 64 向外连续通过 3,240,472 个输入，负侧从 -64 向外连续通过 3,058,769 个输入；各侧均检查 8,388,609 个输入。在首次失败之后，直到 ±128 都没有再次达标的点。扩展正侧的最大达标误差为 `1.847003680e-6`，位于 `x=68.0150604248046875`；扩展负侧的最大达标误差就是上述负端的 `6.674177857e-6`。
结合原有区间最大值 `1.926075618e-6`，整个扩展达标区间的最大误差为 `6.674177857e-6`。

## 失效原因

1. **次正规数打包缺失。** `rtl/exp_fp32.v` 的最终打包直接拼接指数和 23 位 fraction。指数到零时，没有将带隐藏位的完整有效数按次正规数规则右移、舍入。真实值接近 `2^-126` 时误差暂时很小，继续减小 x 就迅速变大。
2. **指数溢出、下溢没有分类处理。** 最终只保留 `output_exp[7:0]`，没有输出 +Inf、逐渐下溢或零的判断。指数会回绕，极小的数学结果可能变成很大的浮点数。
3. **输入幅值仅有 31 位 Q24。** 可保存的幅值上限为 `128-2^-24`。`|x|=128` 时移位结果被截断为零，后续按零计算，因此 ±128 都返回 1。

几个直接 RTL 反例：

| 输入 | 当前 RTL 输出 | 正确舍入 FP32 输出 | 现象 |
|---:|---|---|---|
| -88 | `0003db87` | `0041edc4` | 相对误差约 94.15% |
| -89 | `7f4207dd` | `001840fc` | 应为极小正数，却得到巨大正数 |
| 90 | `00658830` | `7f800000` | 应溢出到 +Inf，却得到次正规数 |
| 128 | `3f800000` | `7f800000` | 幅值截断，返回 1 |
| -128 | `3f800000` | `00000000` | 幅值截断，返回 1 |
| ±最大有限 FP32 | `3f800000` | 正输入为 +Inf，负输入为 0 | 大移位使幅值清零 |

数学真值极小时，“正确舍入成 FP32 的零”与“相对数学真值误差小于 1e-5”是不同指标。前者可以是正确的 IEEE 输出，后者对输出零的相对误差仍为 1。本报告同时记录数学相对误差和 FP32 golden，避免混淆。

## 覆盖与复现

```sh
python3 analysis/range_boundary/run.py
```

只需 Python 标准库和 Icarus Verilog，默认优先使用项目 `.tools/iverilog-12.0/bin/`；也支持 `IVERILOG`、`VVP` 环境变量。

- testbench 直接驱动原始 RTL，逐个枚举从 `0x42800000` 到 `0x43000000` 的全部 FP32 幅值，并分别取正负符号：共 **16,777,218** 个输入，包含 ±64 和 ±128，不采用抽样或二分查找。
- 每个结果与 binary64 `$exp` 比较，分别记录从 ±64 向外的首个失败点、此前最大误差，以及失败之后再次达标的次数。
- 首个失败点周围的相邻 FP32 输入、扩展区间的最坏点、次正规数/零/溢出附近、幅值截断点及最大有限 FP32 共 **271** 个定向输入，再通过信号打印 testbench 验证；`|x|<=128` 的数学参考使用 Python Decimal **80 位精度**复算，更极端的输入直接判定其正确 FP32 输出应为 +Inf 或零。
- `[-64,64]` 的覆盖依据为[原有全区间 Q24 分析](../q_sweep/README.md)，本次没有重新穷举这部分 RTL。`|x|>128` 仅做定向检查；结论是包含零的连续达标区间，不是声称枚举了所有 FP32 编码。
- `results.json` 记录本次 RTL SHA-256、完整扫描计数、边界、最坏点和定向结果；`cases.csv` 是便于查看的定向结果表；`inputs.json` 可直接用于已有调试接口。
- `build/range_boundary/debug/signals.csv` 和 `signal_updates.csv` 包含定向用例的全部 93 个信号、逐次变化以及 RTL/打印 testbench 备份。

原调试工具的 `reference_valid` 仍按原接口 `[-64,64]` 设置，故区间外为 0。扩展范围的 golden 和误差请看本目录的 `cases.csv` / `results.json`，不要把原工具的有效域标记理解成此次没有验证。

运行需要数分钟。生产 RTL 保持不变；修复全范围行为需要另行补充输入范围检查、溢出/下溢分类和次正规数打包逻辑。
